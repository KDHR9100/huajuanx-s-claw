# ADR-0001：人物·事件图谱用 markdown 表格，不用图数据库

- 状态：已采纳（2026-11-01）
- 背景文档：GLOSSARY.md「人物·事件图谱」「浇水」条目

## 背景

`personal/graph.md`（私人区）2026-09-28 起就是一份手工 mermaid 关系网，但 10/10 后无人更新：
求职已闭环仍写「等 offer」、学习线已暂停仍写「停摆」——过时的根源是「图没人浇」，不是缺图结构。
同时记忆页看不见这份图谱（personal/ 不在文件白名单），浇没浇、长什么样全靠盲改。

## 决策

1. **表格即数据源**：graph.md 的两张表（人物节点：节点|圈层|一句话|与轩瑜|来源；事节点：事件|状态|关联人|来源）是唯一数据本体，
   列名固定、列序随意、缺列降级（圈层缺失归「未分组」）；原手写 mermaid 块删除，图一律由页面渲染。
2. **专用通道**：新中间件 `/__rana/person-graph`（服务端路径写死，只放行 graph.md 一个文件；
   personal/ 下其余文件零暴露；前端 mermaid 按需加载，渲染失败降级为提示行）。
3. **只提醒不代干**：维护走人工浇水 + 月度自查提醒，不建自动抽实体建图的机器
   （弱模型抽错难查；图谱内容过云端模型会放大隐私审查风险）。

## 否决的替代方案

- **图数据库/知识图谱系统（MCP server-memory 等）**：量级不够（全记忆 ~1-2MB，直读+向量已覆盖检索）、
  隐私分区会被集中存储放大（heart/querents/graph 三处红线）、弱模型维护不可靠。配置里休眠的 server-memory 保持休眠。
- **手写 SVG 零依赖画图**：开发与维护成本高，mermaid 按需加载的代价可接受。
- **保留 mermaid 块与表格双数据源**：两处记账迟早漂移。

## 后果

- 正面：浇图=改表格（她/主人都会）；图永不过时于数据（页面现算）；隐私分区原样保留。
- 负面：表格只能表达星型拓扑（人/事→中心），人物之间的连线（如家庭危机↔父母）只在文字里，
  图上不可见——数据量大了再考虑「关联人」列建边。
- 负面：mermaid 是较大的前端依赖（按需加载缓解）。
